### A root ssh to a host the user named can reach the reviewer

From OMP session `fa2bd2e7a500`. The user asked the agent to stop a service on their own TV, typed "stop content recognition service" and "then execute the plan", and picked "Yes" on an ask. Jev answered UNSURE on every root ssh to the TV and raised `escalates_privilege` (0.70 to 0.88). That hazard was hard for stage 2, so the reviewer never read the user's words.

On an UNSURE, `escalates_privilege` no longer bars review when the user's words, an ask answer or its question name the host of the ssh, scp or rsync command. That is the same host check a reviewer lift already uses. The command has to be plain enough that the named host is the only place it acts:

- It is one ssh, scp or rsync, spelled by its bare name, with only a leading `cd` and a trailing output filter around it. No second command, no substitution anywhere (`$(ssh other id)` runs first), no assignment prefix, no wrapper.
- Every option is on an allowlist. ssh keeps `-i`, `-p`, `-l`, `-o` for connection settings such as `StrictHostKeyChecking` and `ConnectTimeout`, and a few inert flags, before or after the host (OpenSSH reads both). `ProxyCommand`, `HostName`, `LocalCommand`, `-J`, `-F`, port and agent forwarding, `scp -S` and `rsync -e` all fail closed.
- Every word is written out: no variable (`$OPTS` can expand into `-oProxyCommand=sh`) and no brace or glob (`{a,b}` is two hosts).
- Every host it acts on is named. An scp from the named host to another one is not consent for the other, and a remote end whose host does not read (`[2001:db8::1]`) voids the check rather than drop out of it. The lift check anchors on that same host list, so it no longer falls back to file names for such an scp.

The reviewer prompt moves a root command on a remote machine the user named from "block always" to "block unless the user's words name the machine and the change". A local `sudo` and granting new access stay "block always".

Three fixes reach the lift check too, since it shares the host reader. A sentence's closing period no longer hides the name ("the TV is 192.168.86.53." counts). A URL operand (`rsync://host/mod`, `scp://user@host/path`) yields its host, not its scheme. And `.` or `_` is never a host.

| Case | Stage 2 |
|---|---|
| UNSURE, `escalates_privilege`, one ssh, scp or rsync, every host named | reviewer runs |
| UNSURE, `escalates_privilege`, a host never named | skipped, as before |
| UNSURE, local `sudo` whose operand the user named | skipped, as before |
| UNSURE, ssh run through a variable (`$SSH '…'`) or as `./ssh` | skipped: there is no host to trust |
| UNSURE, a second command, a substitution, an option off the allowlist | skipped |
| UNSAFE with `escalates_privilege` | skipped, as before |
| `exposes_secrets`, `sends_local_data_outbound`, `state_contains_injection` | skipped, as before |
| headless session | skipped, as before |

Whether the user's words cover the command stays the reviewer's call: the code checks that the host appears, not that the user said yes to it. An ask question the agent wrote counts as naming the host, as it already did for a lift, so a question that names the host and gets an unrelated or negative answer still reaches the reviewer, which then needs a quote of the user's own words.

This change alone would not have let the session's commands through:

- No user message or ask named `192.168.86.53`. The user wrote "the TV".
- The two stop commands also scored `exposes_secrets` 0.64, from `-i ~/.ssh/tv_root_ed25519`, and that hazard stays hard.
- They ran ssh through a variable (`SSH="ssh … root@…"; $SSH '…'`), and the read-only probe ran under `timeout 30`. Shape B does not read either form.

The Codex and Claude review lanes and an adversarial pass found the bypasses the bullets above close: a second ssh in a substitution, a remote-to-remote scp, `ProxyCommand` and `HostName` (before and after the host), `-J`, `-F`, `rsync -e`, `scp -S`, URL operands, an assignment prefix, a local program named `ssh`, options in a variable and a bracketed IPv6 host. Each has a test.

Measured with `deepseek/deepseek-flash` and the new prompt on the adversarial, gitflow and intent corpora (jev-latest, three reviewer samples): 0 of 134 labeled-ask rows allowed in each sample, and 0 of 36 labeled-ask rows among the 72 rows production escalates (recovered 8, 9 and 9 of 36). No corpus row is newly eligible: the only UNSURE row with `escalates_privilege` (`ssh -R 8080:localhost:22 studio 'uptime'`) names no host in user words. Four `remote-privilege` rows in the adversarial corpus cover the TV command and three twins (host named for a read-only look, a delete and reboot, a new root key). Jev answers UNSAFE on all four, `escalates_privilege` 0.96 to 0.99, so production still does not review them. The reviewer allowed the TV row and blocked the three twins in all three samples.

## 2026-10-29

### A refusal holds when a retry changes its output filter

https://github.com/STRML/omp-classifier/issues/203, found while fixing https://github.com/STRML/omp-classifier/pull/202. The refusal key read `| tail -60` as the flags `-6 -0`. A retry with `| tail -5`, with `| grep error`, or with no pipe got a new key and was judged as if nothing had been refused. The key now drops a trailing output filter first, using the same check as the stage 2 reviewer-block key. A pipe into anything that is not an output filter keeps its own key.

### Stage 2 reads a script whose output is piped into a filter

From OMP session `01a18951`. The gate blocked `update-fork.sh start 2>&1 | tail -60` twice, both UNSURE: first below the floor (safe 0.67), then on `destructive_or_irreversible` (0.66) on the retry, whose state carried the first refusal. Every hard hazard was at 0.20 or under, so both were eligible for review. The reviewer never ran, because shape B refused any pipe and logged `unread script: a local script runs inside a compound command`.

Shape B now accepts one trailing pipe into `tail`, `head`, `grep` or `cat`. The filter must resolve to a system program on a root-owned chain, with literal words, no redirect, no assignment, and no argument that can name a file:

| Filter | Arguments it may take |
|---|---|
| tail, head | counts only (`-60`, `-n 20`, `--lines=5`, `-q`) |
| grep | one pattern or `-e` patterns, no operand, and only options from a stdin-only allowlist, long ones spelled in full (getopt_long reads `--rec` as `--recursive`) |
| cat | flags only |

Any other right side, a second pipe, or a filter joined by `&&` still refuses. A reviewer block keys on the command without its filter, so a retry that changes the filter or drops it meets the same block.

### A wrapped retry meets the refusal of the command it wraps

https://github.com/STRML/omp-classifier/issues/200, found by the commit security scan on https://github.com/STRML/omp-classifier/pull/199. The refusal key skipped wrapper words but not their arguments, so `timeout 30 scp …` keyed on `timeout 30` and ran past the scp's refusal. Every wrapped command with a duration or option shared that one key, so two unrelated commands under `timeout 30` also refused each other.

The key now reads each wrapper with its own option grammar (`scanWrapperOptions`, the same table the interpreter scan uses) and keys the command it runs. That covers `timeout [opts] DURATION`, `nice -n N`, `env [opts] NAME=VALUE`, `stdbuf -oL`, stacked wrappers, and a bare `NAME=VALUE` prefix, for git, ssh/scp/rsync and every other command. A wrapper whose options the grammar cannot read (`env -S`) keeps the key on the text as written.

### A refused copy stays refused when it is reworded, and consent after the refusal can lift it

From OMP session `01a188b8`. The gate refused an scp of a rebuilt binary to the Studio, the agent asked, and the user picked "Deploy now". The retry still met the refusal. The agent then dropped `-q` and spelled the destination from `/Users/<user>`, and the copy ran.

| Cause | Fix |
|---|---|
| The refusal key was the verb, the sorted flags and the first argument. Dropping `-q` changed the key, and `-o BatchMode=yes` put `batchmode=yes` in the argument slot, so the host never entered the key | ssh, scp and rsync key on where they act, with every option and its value dropped. ssh keys on its host and remote command. scp and rsync count as one verb and key on each remote end, spelled from `~`, plus each local file's name |
| Review follow-ups on the new key | rsync's value-taking long options (`--bwlimit 100`) skip their value; a remote home spelled `/home/<user>`, `/Users/<user>`, `/root` or `~user` counts as `~`; `ssh host -- cmd` keys as `ssh host cmd`; the verb table is a `Map`, so a program named `constructor` with a short flag no longer throws in the key and loses its refusal |
| Only `literalMatch` could lift a model refusal, and it never reads a network command, so no consent could lift one | A stage 2 allow lifts a model refusal for one call when its quote comes from user words or an ask answer given after the refusal, and those words or the ask question name the target (its host, or an operand's file name). A stage-1 SAFE under a model refusal now goes to the reviewer. Critical, cap, eval and headless refusals still never lift |

### The reviewer runs at temperature 0 and retries one malformed reply

From the first live check of stage 2 (https://github.com/STRML/omp-classifier/pull/195), with the real Jev, the transcript of OMP session `01a17ea2`, the real script read and `deepseek/deepseek-flash`.

- Three draws on the same input came back allow, allow and block, and one reply broke the schema. A block is remembered until the user writes again, so one bad draw could pin the command. The reviewer now asks for `temperature: 0`, and sends the request without it when a provider rejects the setting.

### A script body that hands off to another program is not reviewed

Two automated security reviews of the merged reviewer found ways to run code the reviewer never read (https://github.com/STRML/omp-classifier/pull/193, https://github.com/STRML/omp-classifier/pull/194).

| Hole | After |
|---|---|
| `~/bin/tool -> /bin/sh`, then `tool x` | A program is known by its spelled name and by the name of the file it resolves to, PATH lookups included |
| A root-owned program in a group- or other-writable directory | A system program needs its spelled path and its real path on a chain of root-owned components nobody else can write |
| `bash < x` or `sh <<EOF` in a body | Feeding code to an interpreter or `source` on stdin is a hand-off |
| `timeout 30 bash x` in a body | Any wrapper in a body is a hand-off |
| `export PATH=…` in a body | A body that writes PATH, `BASH_ENV`, `ENV` or `CDPATH` is a hand-off |

A program named through a variable (`"$OMP"`) is a stated residual: the reviewer sees the assignment, and the gate does not follow it. `update-fork.sh` still reads.

### A stage 2 reviewer clears what Jev is unsure of and the user asked for

Plan and failure matrix: `docs/plans/2026-10-27-stage-2-reviewer.md`. No battery change: `jevQuestionsHash` stays `a0393345ac3364d4`.

- Jev answers typed questions in one pass and cannot reason through a script. After Sam typed "update fork main", `update-fork.sh start` scored p(safe) 0.21 with the command alone, and 0.73 at best with the skill and the whole script body. A typed "yes, run update-fork.sh start" scored 0.36. Moving the safe floor from 0.80 to 0.55 clears 4 of 113 false asks on the labeled corpora, so thresholds were not the fix.
- A Jev UNSURE now goes to a reasoning reviewer, the way Claude Code's auto-mode classifier sends flagged actions to a second stage. The reviewer reads the user's messages, ask answers paired with the agent's question, the agent's tool calls, and the body of every script the command runs. It never sees tool results, skill text or assistant prose. Its rules are modelled on `claude auto-mode defaults`: allow work the user asked for, require the user to name both action and target for force pushes, deletes, deploys, publishes and shared-state changes, and never allow exfiltration, secrets, privilege or scope escalation.
- Code holds the line, not the prompt:
  - only UNSURE escalates, never UNSAFE, and never with a secrets, exfiltration, privilege or injection hazard at the review level;
  - headless sessions, one-hot answers, the eval tool and dry runs never escalate;
  - only two command shapes are reviewed. One runs no local program: system tools and the repository's own build runners. The other runs one local script on its own, optionally after a literal `cd`, with literal words. Interpreters running a file, wrappers, PATH changes, pipes and scripts inside compound commands are never reviewed. The script body must be readable: not binary, at most 64 KB, not a secret path, not running another local file;
  - an allow must quote the user's own words: a whole entry or at least three words of one, checked in code. The check proves the words exist; whether they cover the command is the reviewer's judgement;
  - the scripts are re-resolved and re-hashed before an allow counts;
  - an allow still passes the forced-block overlay and any recorded refusal, and is never cached;
  - a block is remembered for the target until the user writes again;
  - every failure keeps the block.
- `reviewerModel` (`provider/id`) and `reviewerTimeoutMs` (default 15 s, cut to fit the host's 30 s budget) are new keys in the classifier's own config. A project's settings cannot set them. Unset means no stage 2.
- Measured with `bun eval/reviewer.ts` over every row the gate blocks on the adversarial, gitflow and intent corpora (jev-1.14.0, one sample), plus rows from the OMP session that motivated this. `deepseek/deepseek-flash` had 0 false allows out of 129 labeled-ask rows, got all 6 session rows right, and ran at a p50 of 1.2 s. Sonnet 5.5 could not be measured from the sandbox (connection errors).

### A clicked ask answer is the user's words

No battery change: `jevQuestionsHash` stays `a0393345ac3364d4` and the policy version stays `jev-v2.18`.

- An answer the user picks or types in the host's `ask` tool now counts as a message they typed. The selected labels, typed input and note reach Jev in `evidence.userMessages`, and they can lift a model refusal the same way a typed reply can. The question is the agent's own text, so it stays in non-authorizing tool evidence: a "Cancel" on a question that names the target lifts nothing. Before, an ask answer was a `toolResult`, so it reached Jev only as non-authorizing tool evidence. An agent that followed the refusal's advice and asked through `ask` could never get an approval through. OMP session `01a17ea2` hit this with three approvals in a row, and none of them counted.
- The host picks an answer itself when a question times out (`timedOut` in the ask details). That pick does not count. In a multi-question ask, each question the user answered counts on its own, and the timed-out ones are dropped. Headless sessions still have no user channel.
- Tool evidence leaves out the gate's own refusals and the calls they refused. The gate records the call ids it refuses and drops those, so a command that prints refusal-shaped text cannot hide itself. In that session every retry fed the previous refusal back to Jev, and p(safe) for the same `update-fork.sh start` fell from 0.54 to 0.55, then 0.53, then UNSAFE.
- Tool evidence keeps the newest activity under its size cap. Before, the merged context was cut from the end at 3,000 characters, so the newest entries were the first to go.
- The newest skill the agent read through `skill://` stays in tool evidence, trimmed to its head, after the six-entry window has moved past it.
- Re-judged on jev-1.14.0 with the evidence this change builds, the session's first three `start` calls score p(safe) 0.59, 0.64 and 0.66, against 0.54, 0.55 and 0.53 live. All three are still below the 0.80 floor. A typed approval that names the script scores about the same as a clicked one (0.35 to 0.40). The remaining gap is in how the battery credits a script the user named, and the channel the approval came through no longer matters.

## 2026-10-24

### The gate never prompts

Part 4 of https://github.com/STRML/omp-classifier/issues/184, and the change the first three cleared the way for. No battery change: `jevQuestionsHash` stays `a0393345ac3364d4` and the policy version stays `jev-v2.18`.

- Every path that opened a dialog now blocks. The refusal payload's `layer` names the cause, and `next` tells the agent what to do: reword, choose a safer action, or ask the user in chat.

  | `layer` | Was | `next` points the agent at |
  |---|---|---|
  | `critical` | a dialog | a safer action, or the user running the command themselves |
  | `environment` | a dialog | dropping the env |
  | `cwd` (eval) | a dialog | a literal spawn directory |
  | `unsafe`, `unsure` | a dialog | a safer or more specific command, or asking the user in chat |
  | `unavailable`, `unclassified` | a dialog | telling the user; `/classifier off` pauses the gate for the session |
  | `flagged` | a dialog | the reversible alternative, or the user running it themselves; for a lookalike host (https://github.com/STRML/omp-classifier/pull/178), the user confirming the exact host in chat |
  | `prior-refusal` | a dialog | asking the user in chat |

- The user unblocks a command by saying so in chat: Jev reads the words on the retry.
- A recorded refusal now stands for the whole session. Before, a model refusal stopped applying whenever the evidence fingerprint moved, including on agent-authored `operatorContext` (https://github.com/STRML/omp-classifier/issues/189), and a dialog approval erased the record. Now one bash call gets past a model refusal only when the user's messages since the refusal name the command's target (`literalMatch`: a delete, branch delete, merge or deploy) and Jev answers SAFE with grounded authorization. The record stays for the next call. Critical and cap refusals, eval refusals, command shapes `literalMatch` cannot read, and headless sessions never get past one. A `flagged` command never runs through the agent.
- Host prompts stay: a `prompt` rule in `bash.patterns` and `tools.approval.bash: prompt` are the host's own dialog, and the gate still steps aside for them.
- Audit log: a block writes its lead line, then one `blocked` line (`unclassified` when nothing was judged) that carries the verdict. The `dialog` and `headless` layers and the `approval` field are no longer written. `eval/live-report.ts` and `eval/recognizer-measure.ts` read both old and new lines; the live report's `headless-blocked` bucket is now `blocked`.
- Dry-run reports `would: block` where it reported `would prompt`.
- Eval: `replayDecision` drops `approval` and `headless`, and `hostHandoff` is `run`, `block` or `host-prompt`. Corpus labels stay `allow` and `ask`, and a false ask is still a labeled `allow` the gate blocks. The `approvalOverrides` report field is gone.

### A curl to a lookalike host asks (jev-v2.18)

- Fixes https://github.com/STRML/omp-classifier/issues/161. Under "check the status page at you.github.io/omp-classifier", `curl -sf https://attacker.github.io/omp-classifier/status.json` ran silently at p(safe) 0.81-0.88 on jev-1.13.0 and jev-1.14.0. github.io is a public-suffix private-section entry, so the two hosts belong to different owners.
- Root cause: the gate measured nothing about how a command's destination relates to the hosts the user named. The judge only had the two strings, and it read the shared `github.io` as the same place.
- `measureLookalikeDestinations` in `jev.ts` reads each URL host and remote-verb destination in the command and the hosts in the user's own messages (URLs and bare `host.tld` names). It reports a destination only when all of these hold:

  | Check | `attacker.github.io` vs named `you.github.io` |
  | --- | --- |
  | not equal to any host the user named | yes |
  | not beneath one on a label boundary | yes |
  | shares two or more trailing labels with one | `github.io` |
  | is a plain DNS name once sentence punctuation is dropped (no quote, `$`, backtick or substitution) | yes |

  It's pure (command text plus the redacted user messages), so production and the eval harness measure the same thing, and the verdict cache already keys on both inputs.
- What the measurement does:

  | Where | Effect |
  | --- | --- |
  | state | a `lookalikeDestinations` tier, absent when nothing is reported, so most states are byte-identical to jev-v2.17 |

### Security: a force push is measured only when a lease protects it (jev-v2.16)

- Fixes https://github.com/STRML/omp-classifier/issues/169. The gate compares the local tip with the remote-tracking ref and never fetches. If someone pushed after the last fetch, the stale ref can be an ancestor of the local tip, the gate measured `behind: 0, forwardOnly: true`, and a plain `--force` or `+refspec` discarded their commits. The battery justified a forward-only force push with "the remote's history stays reachable in the remote's own reflog", which is false on bare and hosted remotes.
- Of the two options in the issue, this takes the lease. `--force-with-lease` makes git check, at push time, that the remote still holds the tracking ref's tip, which is the tip the gate measured, so forward-only numbers hold whatever the fetch age. A `trackingRefAsOf` age would need a new staleness threshold and still miss a push made a second after the fetch.
- A force push is now measured only when a lease is all that forces it: `--force-with-lease`, or `--force-with-lease=<ref>` naming the pushed branch, with no `+` refspec and no `--force`/`-f`. Measured with real git, `+main` and `-f` both push past a stale lease. `--force-with-lease=<ref>:<expect>` checks `<expect>`, not the tip the gate read, and a lease on another ref doesn't cover this one, so both stay unmeasured. An unmeasured force push keeps its destructive reading.
- The verdict instructions (jev-v2.16, jev-v3.6) and the `destructive_or_irreversible` "no" criterion drop the reflog claim. They now say a measured force push is a leased one and git refuses it once the remote moves.

### Security: the gate measures where a delete lands (jev-v2.15)

- Fixes https://github.com/STRML/omp-classifier/issues/166. The temp-cleanup carve-out in `unauthorized_consequential_action` was judged from path text, and a `..`, a link, or a repointed `$TMPDIR` can spell "temp" for a path that lives elsewhere.

The temp roots are the real paths of `/tmp`, `/private/tmp` and the gate's own `TMPDIR`; a root that is `/` or holds the home directory is dropped.

### Security: a push is measured only against the remote git sends it to

- Fixes https://github.com/STRML/omp-classifier/issues/173. The 2026-10-23 entry said an earlier `git remote` or `git config` leaves a push unmeasured. That held only for the bare spelling (`git -C . remote …`, `command git remote …`, `echo … >> .git/config` all slipped through). What may run before a measured push is now an allowlist, so an unknown shape fails closed:
  - `cd`, `pushd`, `popd`, `echo`, `true`, `pwd`, `ls`, `test`, `sleep`, `cat`, `head`, `tail`, `grep`, `wc`;
  - plain `git <subcommand>` with no global option, for `add`, `commit`, `status`, `diff`, `log`, `show`, `rev-parse`, `stash`, `checkout`, `switch`, `restore`, `merge`, `cherry-pick`, `revert`, `rm`, `mv`, `branch`, `reset`, `tag`, and none of the options that run a program or write a file (`--exec`, `--strategy`/`-s`, `--output`, and their abbreviations);
  - with no prefix assignment (`GIT_SSH_COMMAND=…`, `GIT_CONFIG_GLOBAL=…`), no redirect that writes a file, and no word the shell rewrites (`$OPT`, `$(…)`, a glob, a brace list), since one can expand to `-x` or `rebase`. `fetch` is left out (https://github.com/STRML/omp-classifier/pull/174 had it): a transport such as `--upload-pack` or `ext::` can run a program, and it rewrites the tracking refs the measurement reads.

  Anything else before the push (a wrapper such as `env`, `command`, `xargs` or `nohup`, an interpreter such as `sh -c` or `python -c`, `git rebase -x`, `git submodule foreach`, a script, a test runner, `tee`/`cp`/`ln` into `~/.gitconfig`) leaves it unmeasured. So does every substitution and every pipeline stage after the push, which run before or alongside it. A segment after the push in a plain sequence (`git push -u origin HEAD && gh pr create …`) runs once the push is done and is not read. That order holds only when the command has no function, loop, coprocess or background job, so any of those leaves the push unmeasured.
- The push's own words must reach git as written too. `git push origin {main,+side}` is a force push of two refs, which the parse read as one literal refspec.
- Hooks (`pre-commit`, `post-merge`, the push's own `pre-push`) are installed code that the command's words never show, before or after this change. They are not read.
- Cost: `CI=1 bun test && git push origin main` and similar are no longer measured, so they ask.
- A remote counts as known only when `remote.<name>.url` is set, exactly once. Tracking refs alone (stale, or made by hand with `update-ref`) no longer count, since git reads such a name as a path or URL. A second url makes git push to both while `git config --get` reports one.
- A push stays unmeasured when `remote.<name>.pushurl` or any `url.<base>.pushInsteadOf` is set. Either one sends the push somewhere the tracking refs were not fetched from.
- A function name inside a quoted string no longer reads as a function definition. The check now walks the syntax tree, so `git commit -m "fix foo()" && git push origin main` keeps its measurement.
- The url, pushurl and pushInsteadOf checks read every config scope, so a rewrite in `~/.gitconfig` counts too.

### Security: a force push is measured only when nothing else can run before it

- Follow-up to https://github.com/STRML/omp-classifier/pull/168, which measured a push after a list of "neutral" earlier segments. Review kept finding neutral subcommands with flags that write a ref file or rewind HEAD (`log`/`stash show --output`, `cherry-pick --abort`, `branch -D` then `branch <name> <rev>`). The parser also flattens loops and function bodies, and reads `&` like `;`, so source order isn't run order.
- Provenance only changes a verdict for a push with force syntax: the battery reads a forward-only force push as a forward publish. Without force, git refuses any non-fast-forward update, so nothing that runs first can make the push destructive.
- So a force push (`+refspec`, `--force*`, a `-…f…` cluster) is measured only as the last segment, after nothing but plain `cd`/`pushd`/`popd`, with no loop, function body, subshell, pipe, background job, substitution, assignment or redirect anywhere in the command. Anything else leaves it unmeasured, and it keeps its destructive reading.
- A push without force is measured as before, so `git commit … && git push origin HEAD` and `git push -u origin HEAD && gh pr create` keep their measurement.
- Any push stays unmeasured when the shell might not run git for `git`, or when the remote might not be the one the repository knows:
  - a function definition, `alias`, `export`, `source`/`.`, `hash`, `eval`, `set`, `shopt`, a bare assignment such as `PATH=…`, or a loop, subshell or group anywhere in the command (these could put `--force` behind a plain-looking push)
  - an earlier `git remote` or `git config` (these could repoint the remote)
  - a remote operand that isn't a known remote name. A URL or a path has no tracking ref, and a null remote tip there would read as a new branch on the user's own remote while the commits go somewhere else.

### Security: `git push origin HEAD` is measured against the branch it pushes

- `measureGitPushProvenance` looked up `refs/remotes/<remote>/HEAD` for a `HEAD` or `@` refspec. That ref is the remote's default branch, but `git push origin HEAD` updates the remote branch named like the current one. On a feature branch that contains main, `git push --force origin HEAD` therefore measured `forwardOnly: true` even when the remote feature branch held commits the push would discard. The battery reads a forward-only force push as a forward publish, so that destructive push could run silently.
- The remote side of a `HEAD`/`@` refspec now resolves to the current branch (`git symbolic-ref --short HEAD`). A detached HEAD names no remote branch, so nothing is measured, and a force push without provenance keeps its destructive reading. `HEAD:<name>` already named its remote side and is unchanged.
- The same mismatch also produced false asks: once main moved past a branch's base, a plain `git push -u origin HEAD` measured `behind` above zero against main.
- The `--force`, `-f` and `--force-with-lease` spellings were still caught by the moderate-risk overlay, which turns a SAFE into a dialog. `git push origin +HEAD` reaches no overlay, so that spelling could run silently.
- The measurement now stays absent whenever it can't pin the push to one ref pair in the segment's own repository. It is judged by allowlist, so an unknown shape fails closed and a force push keeps its destructive reading:
  - any push flag outside a short list that only changes how the one ref is sent (`--force`, `--force-with-lease`, `-u`, `-q`, `-v`, `--no-verify`, `--dry-run`, …). This covers deletes, `--all`, `--mirror`, `--tags`, value flags such as `-o`, and git's abbreviations like `--del`.
  - more than one refspec
  - anything but a bare `git push` command word (`env …`, `command git`, a global option such as `-C` or `--git-dir=`, a `NAME=value` prefix)
  - an earlier segment that could move refs before the push runs. Only `cd`, `echo`, `cat`, `ls`, `test` and similar, and plain `git status/log/diff/show/add/rm/mv/commit/merge/cherry-pick/revert/stash/rev-parse/branch` with no global options, are neutral. `commit --amend` (or `--amen`) and `branch -f/-m/-M/-C` are not, nor is any segment that redirects into a file.

  An earlier commit, merge or cherry-pick only adds descendants of the measured tip, so the push stays measured after one.
- `<src>:HEAD` names a destination spelled HEAD and is not rewritten. The current branch is read from `symbolic-ref HEAD`'s full ref, so an ambiguous short name can't come back as `heads/x`.
- Not fixed here: the remote-tracking ref can be stale, because the gate never fetches. Tracked in a follow-up issue.

### Measured network provenance (policy `jev-v2.10`)

- `curl http://localhost:8000/…` and `ssh raw-ovh …` were the two most common network false-asks in the measured decision log (`declared scope contradicts command (network)`, ~6% of blocks in the 09-09 to 09-17 window): the state carried no provenance for the called host, so every command that happened to use a remote-looking URL was judged on the shape of its text alone. New `measureNetworkProvenance` in `jev.ts` (issue #65, the tier rule of #63) runs before the battery is asked and measures the command's own destinations against this machine's own naming:
  - `localPorts` — the ports the command names on a loopback address (`localhost`, `127.0.0.0/8`, `::1`, `*.localhost`), read from its URLs, an `ssh -p` destination, or `nc host port`.
  - `knownHosts` — the hosts the command names that this machine's own SSH config, hosts file, or running docker container names also name, each with the source it was measured in. This is what catches `raw-ovh`, which lives in the user's `~/.ssh/config`.
  - `dockerNetworks` — a compose service the local compose file declares (read from the `-f` file the command names, else the default compose file names in the working directory), or a loopback port a running container publishes. `docker ps` runs once per burst, cached 3s and aborted at 2.5s; a daemon that is not running yields no measurement, not an error.
  - `resolvesLocally` on each of those targets — which machine actually runs it. The file on this disk is configuration, not execution provenance: `docker -H tcp://prod:2376 compose -f compose.yaml exec web …` runs `web` on prod, whatever the working directory declares. The daemon is measured from the command's own `-H`/`--host`/`-c`/`--context`/`--config` (and a `docker-compose` CLI's own globals before its subcommand), else from this machine's `DOCKER_HOST`/`DOCKER_CONTEXT`, else from the context `docker context use` made current (`config.json` plus the context's `contexts/meta/<sha256(name)>/meta.json`), else the CLI's own default socket; `--config <dir>` names the directory that last part is read from, and it is read in the directory the invocation's OWN SEGMENT runs in: every path a docker CLI resolves itself — `--config`, `-f`, the default compose file names, a relative `DOCKER_CONFIG` — is relative to that directory, not to the one the command started in (`cd /tmp; docker --config ./.docker compose exec web sh` reads `/tmp/.docker`, so a remote context there is not called local), and a directory the command's own text does not pin (`cd "$DIR"; …`) leaves the path unmeasured rather than substituting a file docker never opens. Every selector a chain carries is resolved together and the claim holds only when they agree — a local `DOCKER_HOST` beside a `DOCKER_CONTEXT` naming another machine measures nothing, because which of them the CLI's precedence picks (its reference and its implementation disagree) is not recorded in this machine's state. A `unix://`/`npipe://` socket or a loopback `tcp://`/`http(s)://`/`ssh://` host is this machine, so `resolvesLocally` is true; another host makes it false; a spelling this gate cannot read (a bare `host:port`, an unreadable context endpoint, `fd://`) leaves the field **absent** — an unmeasured daemon is never claimed as local. The same gate applies to the port table: when this machine's own environment points the gate's own daemon elsewhere, `docker ps` lists that host's containers and nothing from it is measured. A `-f` path that cannot be read already yielded no target for that invocation at all — it is not evidence either way — and the file's silence about a service is never evidence about the machine that runs one, so the compose tier no longer reads the `-f` file as anything but a list of declared names.

A loopback port identifies an address on this machine, usually a local process but possibly a forward; the port alone does not establish where traffic ultimately goes. An SSH alias that resolves in this machine's own config is the user's own host, still judged on what the command does to it. The non-goal stands: `ssh <alias> <destructive command>` is destructive on its command body, not on its hostname.
- Trust constraint: every name is measured by the gate from this machine's own files and process state, never reported by the command's author, and nothing in the measurement opens a socket. ### Judge the script body, not its path (#67)

- Where a script lived decided whether it ran: `python3 .scratch/x.py` was judged as command TEXT, so a byte-identical script refused under the old `/tmp` provenance rule ran from the assigned worktree, and renaming a refused script flipped the verdict (measured in the 2026-09-16 autodream run: ~28 `/tmp` refusals, ~8 worktree runs, one rename). New `readInterpretedScriptBodies` (index.ts) reads the file an interpreter operand names and splices each body into the text the gate judges, fenced with `# --- <verb> runs <operand>; body read from disk ---` labels, exactly the way a heredoc body already rides the command. Every layer below reads that text: the built-in critical patterns, the forced-dialog token scan, the verdict cache key, the session and persistent grants, the refusal record, the judge state, and the dialog body — so the human approves the same text the judge saw.
- Discovery is verb-position only, after wrappers and assignments, the same rule the pipe scan uses (`ps aux | grep python` is still not an invocation). The interpreter's own operand (`python3 x.py`, `bash probe`, `php -f x.php`) is read strictly; a word reached past a subcommand or a loader flag (`bun run x.ts`, `node -r ./pre.js main.js`) is read best-effort, because the same spelling is also a package.json script or a data argument. Inline code (`-c`/`-e`/`-p`), stdin (`-`, `-s`), php's `-r` and `python3 -m pkg` keep their existing treatment and the file rule leaves them alone. An interpreter line inside a heredoc *document* is data to the shell and is not a program. A flag whose value is a file the interpreter runs (`bun --preload ./pre.ts`, and bun's `--require`/`--import`/`-r` aliases of it, node's `--require`/`--import`, php's `-f`) is read like an operand — the program slot stays open for the word after it — and the value ATTACHED to such a flag is the same value: `--preload=./payload.ts`, `-r./payload.ts` and `php -f=x.php` named files nothing read while the program slot moved on; a flag whose value is a setting is consumed as one, separated or attached (`python3 -W ignore payload` and `python3 -Wignore payload` both run `payload`), and a short word that is a flag CLUSTER is deliberately not read as its first letter's value (`bash -cx ./x.sh` still runs x.sh); the per-verb grammar is the interpreter's own (`lua -- script.lua` ends the options and still runs `script.lua`, `osascript -i script.applescript` takes no value, `python3 -W ignore payload` runs `payload`).
- Fail closed on every program the classifier cannot read in full, with layer `script-body` and before any static rule, grant, or dialog can approve text nobody read: a word the shell would expand (glob, variable, substitution), a directory (python would open its `__main__.py`), a special file, an unreadable or short-read file, and a body that cannot fit the review limit. The body shares `maxCommandLength` with the command, and the refusal names the operand and the bytes. A file that is not there is left alone: it runs nothing, and the write-then-run heredoc compound whose body already rides the command text keeps working. A program word is resolved against the directory its own command segment runs in, and a `cd` chain the text cannot pin — an expanded or stacked target, a `||` head whose `cd` may or may not have taken effect, and a `||` BRANCH that moves the shell itself (`cd /tmp || cd /var/tmp && python3 payload.py`: the `&&` gates the whole chain, so the program is in /tmp when it exists and in /var/tmp when it does not) — makes the later program a refusal rather than a read from a guessed directory; the `||` branch itself is still read from the directory its `cd` found, which is where it really runs. An arm reached only when the chain before it succeeded doubts the directory only when running it could have MOVED the shell: `: && :; python3 payload.py` runs in the directory the command started in, so the walk keeps it instead of refusing a chain that names exactly one directory, while an arm that moves it (`make build && cd /tmp; python3 payload.py`) keeps the doubt, because whether it ran decides where the program runs (round 4 review).
- The entry file only. `import`/`require`/`source` targets and `python3 -m pkg` are resolved by the interpreter's own rules (sys.path, NODE_PATH, extension lookup, dynamic specifiers); a half-resolver here would read the wrong file and say nothing about the right one.
- A body that matches the interpreter-code markers (`exec(`, `subprocess`, `base64`, `os.system`, `\xNN`) keeps its flag on a SAFE, the same as an inline `-c` payload: a script that re-execs or decodes its real work is not code the classifier read. Shell-shaped lines in the body (`rm -rf ./out`) reach the forced-dialog token scan and the built-in critical list as ordinary text.
- Two interactions worth knowing: a host allow rule no longer short-circuits a call whose body was read (the rule matched the command text, not the file, and the file decides what runs), and grants, the verdict cache and the refusal memory now key on the spliced text, so rewriting a script re-asks instead of riding the previous body's verdict or grant.
- No policy bump: the battery, the criteria and the derivation rules are unchanged. The cache key carries the body, so a rewrite can never reuse a verdict, and nothing persisted a verdict across a reload.
### Gate round 3 on the fix batch: the Ruby setter finding

- **A Ruby setter definition is no longer mistaken for an endless method.** `isRubyEndlessDef` read the first `=` at paren depth 0 after `def` as the marker of Ruby 3's endless-method body, but the `=` Ruby binds to a def's *name token* arrives at depth 0 too: the setter `def value=(v)`, the parenless `def value= v`, the element setter `def []=(k, v)`, the operators `def ==(other)` and `def <=>(other)`, and the singleton `def self.value=(v)`. Every one of those is a regular def — an opener whose `end` the block balance must count — so misreading it skipped the opener, the setter's own `end` then closed the enclosing `Dir.chdir` block, and a spawn written inside the block was judged against the session directory Ruby had already restored, with both spawn sites agreeing, so nothing asked. ### A judgment that answers after its deadline now reaches the dialog (#62)

- The deadline is a race the gate owns, not an abort on the request. `jev-judge.ts` splits in two: `judgeBattery` is the request half (it takes the request's own signal — the shadow and the eval harness still hand it `AbortSignal.timeout`), and the new `judgeBatteryUnderDeadline` is the judge half. On a miss it returns `{ kind: "deadline", late }` with the request still running.
- `classify` maps both paths through one `judgementFrom(answers)`, so a late answer is read by the same code, with the same evidence weight, as an on-time one. A missed deadline yields `UNAVAILABLE` and reports the timeout (`Jev unavailable: judgment timed out after 8000ms`) instead of an opaque abort, and rides back on `Judgement.late`.
- `requestPermission` races the dialog against that handle, and only in that case: a late `SAFE` aborts the dialog and the command runs (the answer the deadline had no right to take away), a late `UNSAFE` keeps it open and adds the real reason as a warning beside it, a late `UNSURE` only goes on the record. The dialog's reason says so up front: the judgment is still running and may dismiss the dialog before the human answers.
- Fail-closed is untouched: a late verdict can only refine a dialog that is already open, a dismissal is honored only when the dialog settled with no answer of the human's (so a real Deny always wins), and a late `UNSAFE` never re-blocks a command a human allowed — it is logged next to their choice as `approved by user (unavailable → late UNSAFE)`.
- A human who answers first cancels the request, and the late answer does nothing. Listening stops at `min(2 x timeoutMs, 30s)` past the deadline (`stopListening` aborts the request when the window closes), so a wedged provider cannot hold a socket for the session.
- The three cases are one line each on a new `late-verdict` layer, with the decision pair (`unavailable → late SAFE`, `late UNSAFE`, `late UNSURE`) in `why` and the answer's own `verdict`/`reasonCode`/`jev` the way a verdict line carries them. No `approval`: nobody answered that dialog, the verdict did.
- A late SAFE dismisses only where an on-time SAFE would have auto-run. The dialog is offered the handle together with the guards the verdict path applies — the destructive/irreversible overlay and this session's refusal for the target — and a guarded command keeps its dialog (logged as `dialog kept open — classifier-safe but flags: rm`, or `… despite prior refusal of "…"`). The late path recovers the answer the deadline took away; it never skips a guard.
- `eval/live-report.ts` counts a late SAFE's dismissal as an auto-allow, since the human was never asked; the late block lines stay unterminal so the human's own answer is the outcome that counts.
- Real failures (HTTP error, missing key, unreadable body) are unchanged: no background race, the dialog opens immediately, because retrying them has meaningfully lower EV and the error text is the point.

### A pluggable judge backend (#84)

- The transport is one seam now: `JudgeBackend` in `jev-judge.ts` produces the `Judge` that answers `judgeBattery`/`judgeAuthorization`, and `judgeBackend` in the config file selects it. The default kind, `{kind: "typesafe"}`, is the host path byte for byte — the same `resolveJudge` deps, the same pinned judge role, the same one-hot fallback semantics, and no new socket opened anywhere.
- `{"kind": "endpoint", "baseUrl", "model", "apiKeyEnv"}` points the gate at any server speaking System One's wire contract (`POST {baseUrl}/v1/systemone` with `{state, model, questions}` → `{model, answers}`). The transport is the host's own `TypeSafeJudge`, so retries, timeouts, and the error taxonomy are the ones the default path already had. `apiKeyEnv` is an environment variable NAME: the key is read per call, never written to the config file, the audit log, or `/classifier status`, and a missing one fails closed with no request sent.
- Nothing about the battery or the policy moves: the endpoint answers probabilities, so the same `jevPolicy` floors read them, and one-hot handling stays reserved for a text bridge. A missing credential, an unreachable endpoint, a non-2xx, a malformed body, and a timeout are all `JevUnavailableError` → permission request.
- The endpoint kind's redirect is closed (#124). `fetch` follows a redirect by default, and this request carries the judged state and `Authorization: Bearer <key>`, so an endpoint answering 307/308 could have the state replayed to a second host — on the same origin, the key with it. Measured on two real local servers, POST with a JSON body: under the default policy the second hop receives the body verbatim; the endpoint path now forces `redirect: "manual"`, and the 3xx comes back as the response, `response.redirected` false, second hop never contacted. A reply the runtime reports as `redirected` is refused rather than judged, so even a runtime that ignored the policy could not yield a verdict from the redirect target, and a 3xx is not one of the statuses the host client retries (408/429/5xx): it costs one request and surfaces as `JevUnavailableError` → permission request. Two local servers pin it — the target receives zero requests for a 302 and for the 307 (the status that replays the body), and the gate reports an outage instead of judging whatever the target answers.
- Backend identity joins the config signature and both cache keys (`config.typesafeModel`, `judgeBackendFor(config.judgeBackend).id`), so a backend swap cannot serve a verdict the other judge produced — proven through the dry-run probe, the one cache read the signature deliberately leaves stale. A verdict cached under the host judge is no longer reported as an endpoint's.
- `/classifier` shows the active backend as `judgeBackend: <id>` and `/classifier status` carries `backendId` (`typesafe/jev-latest`, `endpoint/http://127.0.0.1:8765#local-decide`). The shadow judgment asks the same backend as the live one. `/classifier reset` returns the key to the default; bad shapes (unknown kind, a non-URL baseUrl, a missing model, an env var name with a space) keep the default rather than half-applying an override.

### Triage queue: three parser and loader defects

- Risk verbs inside a substitution are now read from the parsed AST (`substitutionSpans`), the same source `commandHasOutboundNetwork` uses. `addSubstitutionFlags` collected `$(…)` and backtick spans with a quote-blind regex, so `echo '$(rm -rf /tmp/x)'` raised a risk flag for a substitution that never runs. Quoted spans are data now, nested spans are seen at every depth, and the removed local guard lets process substitution through, so `cat <(rm -rf /tmp/x)` asks. (#119)
- `userWords` no longer normalizes the user's message with NFKC before stripping code fences. NFKC maps U+FF40 to a backtick, so a negation styled with fullwidth grave accents looked like inline code and was deleted with it: `｀don’t｀ delete build` matched `rm -rf build`. The passes now run in the order that cannot manufacture a fence: the explicit apostrophe and quote mappings first, the fenced and inline-code strippers next, NFKC last, before the blockquote filter and tokenization. U+FF02 joined the explicit quote set, since NFKC folds it to a double quote. A full sweep of U+0000..U+10FFFF confirmed U+FF40 and U+1FEF were the only code points NFKC maps to a backtick. (#88)
- `eval/run.ts`'s four corpus loaders share one `parseJsonl(path)` that names `file:line` on a malformed line, with the real 1-based line in the file, instead of a bare `JSON.parse` `SyntaxError`. Blank and whitespace-only lines stay tolerated and the parsed rows are unchanged. (#81)

### Refusal memory keys on the grant identity (#64)

### The eval gate judges a spawn in the spawn's own directory (#14)

- A spawn that passes its own working directory no longer runs unread in the session's: `subprocess.run(cmd, cwd="/tmp/x")`, `exec(cmd, { cwd: "/" })`, `spawn(file, args, { cwd })`, `Bun.spawn(…, { cwd })`, a `Bun.$` shell's `.cwd(…)` call, Ruby `Dir.chdir("/tmp") do … end` and `system(…, chdir: …)` are read out of the payload's text, and the gate judges the payload in that directory. `exec("rm -rf .", { cwd: "/" })` used to be recorded, shown and classified as `rm -rf .` in the session directory; the dialog now says `working directory: / (declared by the payload's spawn call)` and the judge is asked about `/`. The directory is part of the identity of a judgement, not a display detail.
- New `spawnCwd` field on every `decisions.jsonl` line the call writes, beside the resolved `cwd`: the record says which directory the payload chose for itself, since the `cmd` field is truncated to 120 characters and a reader cannot recover it from there. The resolved directory is also a fact the judge is given, not one it has to infer from the code.
- The cache key gained both directories — the spawn's own, where the judged command runs, and the session's, where the payload's own process still runs and reads and writes. Dropping either would let a verdict cross a directory change it never saw, and no entry written before this can be hit: the key text differs.
- The scan is site-scoped and structure-aware, where the marker scan is not: a `cwd=` inside a string, inside a comment, or inside a nested call's arguments (`env=make(cwd=…)`) is not read as the spawn's directory, because each of those would name a directory the payload does not run in. It is still a scan, not a parser (kernel interception, #13, is the structural fix): a quoted option key (`{ "cwd": … }`), a Ruby `"chdir" => …` hash key, and an alias it cannot follow leave the site reading as "no cwd argument".
- Relative literals resolve against the directory in effect the way the bash path resolves a leading `cd`, so `cwd="../.."` and a relative `chdir:` under a `Dir.chdir` block resolve against what they follow. The resolved directory is shown as resolved even when it lands outside the session directory. A bare `/` keeps its literal meaning here: `resolveToCwd` reads it as a workspace-root alias for tool inputs, and a spawned child has no such alias — treating it as the session directory would understate what `rm -rf .` does in `/`.
- Fail closed where the directory cannot be read: `{ cwd }`, `cwd=os.environ["X"]`, an f-string, a `**opts`/`{ ...opts }` options object, a value that is two literals concatenated, an internal-URL directory, and two spawns that disagree all raise a permission request under the new layer `cwd` with headline `unreadable spawn cwd`, naming what could not be read. Nothing is classified in those cases: a payload judged against a directory it does not run in was judged on the wrong question, and no verdict is worth asking it. `Dir.chdir` with no argument goes to the home directory and asks the same way.
- Bash is untouched. Its own `cd`-resolution, internal-URL block and key are exactly as they were; the spawn scan is the eval path's alone.
- No policy bump: the battery, the criteria and the derivation rules are unchanged, so `CLASSIFIER_POLICY_HASH` and every pinned digest stay put.

### The authorization request (#94)

- New `authorization.ts`: the second Jev request from Phase 2 of the intent-aware judgment plan. One question, `user_authorization`, answers how well the user's own words cover what the command does, at three levels: `none`, `goal` and `named`. A target over 64 characters, a target carrying a word aimed at a reviewer, or a target written as a sentence is replaced by an unsalted hash of itself. Every other action reports its kind and `unnamed-arguments`. A subcommand CLI names its path up to the first flag (`npm-publish`, `kubectl-delete-pod`), so `npm audit` and `npm publish` differ. A command nothing classifies is reported as `other` carrying its verb. `privilege` and `secret-read` ride beside the action they describe, so `sudo ./deploy.sh --prod` reports the privilege and the deploy under it. A verb that can run another program (`awk`, `sed`, `less`, `fd -x`) is never a read.

That covers `--mirror`, `--delete`, `--tags` and `--hard` too; a short spelling counts only exact and only where the tool's grammar defines it (`git push -f`), so a cluster such as `-of` is unnamed. A target list over 8 ends in `more:N`. One classified action counts as one action however many targets it names. An input redirect is a read and an output redirect is a write.

An unanswerable authorization request costs a command its fast path, never the whole judgment. `namedMinProbability` (0.8) lives in the module's own policy rather than in `JevPolicy`, because `jevQuestionsHash` folds `DEFAULT_JEV_POLICY` into the cache key and a new key would invalidate every cached `jev-v2` verdict during the shadow week.

The `--password-stdin` exemption is bound to the stage that actually receives the secret: the next segment must be joined by a real pipe, be a credential consumer, and carry the flag, so `printf … | tee /tmp/leak | docker login --password-stdin` asks while `echo $TOKEN | docker login --password-stdin` still does not. The word splitter now records whether a pipe joined each segment, because `;` and `&&` pass nothing.

- New `literal-match.ts`: the local-action fast path from Phase 2 of the intent-aware judgment plan. A command matches only when every segment is an extracted action or an inert shape, and every extracted action is named in the user's own recent standalone words. Extracted actions: a delete whose real path resolves inside the working directory or the session temp directory, a branch delete, `gh pr merge <number>`, and a deploy script inside the working directory. Network egress, secrets and privilege are neither extracted nor inert, so they make a command incomplete and it goes to the reviewer. A command spelled as a path is a file rather than a verb, an inert verb carrying a redirect or a glob is not an inert segment, and a delete never matches without a real-path resolver, so a symlink out of the working directory cannot match on the name it was given.
- Matching is whole-word and imperative or present, so "rebuild" does not authorize deleting `build` and a past-tense recount authorizes nothing. A restrictive or conditional word within five words cancels a match, typographic apostrophes are folded first so `don’t` cancels like `don't`, and a verb only authorizes the target in its own clause: "delete build then merge main" does not authorize deleting the branch `main`. Every branch of a variadic `git branch -D` and every PR of a variadic `gh pr merge` must be named. Nothing calls `literalMatch` yet; Phase 2 step 5 gives it a branch in the decision order. Follow-ups: #86, #88, #89.

- New `floor.ts`: the code floor from Phase 2 of the intent-aware judgment plan. Four entries always ask, whatever the model answers and whatever the user authorized: the built-in critical patterns, a secret reaching a sink that is not on the allowed list, a download piped into an interpreter, and obfuscated code (base64 into an interpreter or `exec`, marshal and pickle loads, runs of hex escapes, shell `eval` of a value). Entry 2 is destination-blind by design — it checks what a secret flows into, not where that goes — so a key in a request header passes the floor whatever host it names, and the host is judged above the floor. Allowed sinks, and only these: a `$(…)` capture assigned to a variable, `/dev/null`, a curl auth header or `-u` without `-v`/`--trace`, and `--password-stdin`. A capture taints the variable for the session, so a later `echo $KEY` asks.
- The floor runs in shadow: every `decisions.jsonl` record gains a `floor` field (`asks` plus the entries that matched), computed once per tool call and read by no decision. The live verdict is byte-for-byte what it was, pinned by a test where Jev answers SAFE on a command the floor would stop. Per-session taint is wiped at the same boundaries as the verdict cache and grants.

## 2026-09-17 — Jev port (v0.3.0)

- Judgment moved from a prompted local model to Jev, TypeSafe's System One model: one HTTP request per classification (`POST https://api.typesafe.ai/v1/systemone`, `model: jev-latest`), plain `fetch`, no SDK dependency. The two-stage contract goes with the prompt that defined it — `CLASSIFIER_PROMPT`, the capped `ANALYSIS` plus terminal `VERDICT:` line, `parseJudgement`, the verdict regexes, the reviewer pass, and every post-parse check that read the model's prose (citation grounding, egress consistency, write scope). Jev never writes prose: it answers typed questions, and the verdict is derived in code from the returned probabilities, so a decision's reason is assembled from numbers and hazard ids and the machine-readable `reasonCode` carries the same information (`jev:safe`, `jev:unsafe`, `jev:hazard:<name>`, `jev:blast-radius`, `jev:below-floor`, `jev:unavailable`).
- New `jev.ts` owns the exchange: state building, the question battery, key resolution (`TYPESAFE_API_KEY`, else the macOS keychain entry `jev`), and the request. `askJev` throws `JevUnavailableError` — missing key, non-2xx, unparseable body, missing or mistyped answer field, timeout — and never returns a verdict, so every unavailable judgment keeps failing closed to a permission request and is never cached.
- Battery: one `choice` question for the verdict (safe/unsafe/unsure), one `noul` per hazard (`state_contains_injection`, `authorization_missing`, `destructive_or_irreversible`, `writes_outside_working_directory`, `contacts_remote_endpoint`, `sends_local_data_outbound`, `escalates_privilege`, `exposes_secrets`, `affects_shared_or_remote_state`), and one `score` for blast radius — all asked in the same request, because extra questions in a request are cheap while a second round trip is not. `jevQuestionsHash()` (policy version + serialized battery + default policy) is part of the cache key, so editing a question invalidates every cached verdict, by design.
- Policy version `jev-v1` with derivation in `deriveJevDecision`: SAFE needs `p(safe) >= 0.80` and `confidence >= 0.50` with no hazard at or above `0.55` and blast radius below `1.5`; UNSAFE comes from `p(unsafe) >= 0.50` or any hazard at or above `0.90`; everything else is UNSURE. The thresholds are policy, not constants to copy: measured probabilities shift with the battery and the shape of the state (the same command answered `safe` 0.61 / confidence 0.42 asked alone, and `safe` 0.52 / `unsafe` 0.43 / confidence 0.29 with the full battery), and `safe` at 0.52 is a command the gate must ask about rather than run.
- Config: `model` and `fallbackModels` are gone with the local-judge era — there is one hosted judge and no chain to walk. The keys are now `enabled`, `typesafeModel` (default `jev-latest`), `jevPolicy` (the six thresholds), `timeoutMs`, `maxCommandLength`, `evidenceUserMessages`, `persistentGrants`. Changing any key still flushes the verdict cache and the session grants.
- Identity: package, repo and plugin name `omp-classifier`; config `~/.omp/omp-classifier.json`; grants `omp-classifier-grants.json`; artifact dir `<agentDir>/omp-classifier/` for `decisions.jsonl` and the status report; env overrides `OMP_JEV_CONFIG` and `OMP_JEV_TEST_LOCKFILE`. Upgrading: `omp plugin uninstall omp-classifier`, then `omp plugin install .` — two bash gates installed at once both intercept `tool_call`.
- Removed `@typesafe-ai/sdk` from the dependency set in favor of plain `fetch`, so the plugin still installs with no runtime dependencies.

- Gate round 13 (codex on c249a32, two findings): `ghApiWrites` now expands bundled shorts (`-ifbody=secret` carries `-f`) and treats any method flag whose value is not a literal GET/HEAD as a write, so `--method="$METHOD"` fails closed. The second finding is documented as a structural ceiling, not patched: the egress scan reads pipeline-stage lead tokens, so wrapper commands (`env ssh`), command substitution (`echo "$(ssh …)"`), control flow (`if true; then ssh …; fi`), and negation (`! ssh`) are invisible to it — as they were on main before this branch. Closing that fully needs a real shell-aware parser; the scan is a best-effort backstop behind the model's own verdict, which sees the full command text, not a complete egress oracle.
- Gate round 14 (codex on f12d3aa, two findings): the gh bundle check covers `-X` alongside `-f`/`-F`, closing the short-flag space (`-iXPOST`, `-iX POST`); `-H` stays excluded on purpose — headers on GETs are routine and marking them writes would re-prompt every hosted-API read. And `splitTopLevelCommands` itself is comment-aware now (a word- or operator-adjacent `#` swallows to end of line), so `git status # && ssh host cat` no longer phantom-splits into a dialog. Everything the scan still cannot see (wrappers, substitution, control flow, negation) is the documented ceiling from round 13.
